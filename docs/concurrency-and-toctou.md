# خريطة نقاط التسابق البرمجي وفحص الوقت للاستخدام (TOCTOU Map)

في الأنظمة الإدارية المؤسسية ذات الضغط المتزامن، تحدث ثغرات **TOCTOU (Time-of-Check to Time-of-Use)** عندما تقرأ الخدمة حالة كائن من قاعدة البيانات، ثم تفحص شروط العمل برمجياً في الذاكرة (Memory Check)، ثم تُجري التعديل في قاعدة البيانات في خطوة تالية دون قفل ذري أو تزامن متفائل.

توضح هذه الوثيقة خريطة الثغرات التي تم رصدها ومعالجتها في نظام إدارة المراسلات:

---

## 1. ثغرة الإحالة المتزامنة المزدوجة (Concurrent Referral Race)
- **الموقع:** `src/referrals/referrals.service.ts` -> دالة `create()`.
- **المسار القديم:**
  1. قراءة المراسلة `corr = findUnique(...)`.
  2. فحص `canRefer(user, toUser, corr)` في الذاكرة.
  3. الدخول في `$transaction` وإنشاء الإحالة وتحديث المراسلة بـ `update({ where: { id } })`.
- **سيناريو التسابق:**
  - وصول طلبي إحالة متزامنين لنفس المراسلة (`Request A` و `Request B`).
  - كلاهما يقرأ المراسلة في حالة `RECEIVED` مع `version = 1`.
  - كلاهما يجتاز فحص `canRefer` بنجاح في نفس اللحظة.
  - النتيجة: إنشاء إحالتين مفتوحتين لنفس المراسلة لأطراف مختلفة في تعارض صارخ لدورة العمل!
- **الحل الجذري المطبق:**
  - دمج التحقق داخل المعاملة ذرّياً عبر `updateMany({ where: { id, version: corr.version, status: { in: referableStatuses } }, data: { version: { increment: 1 }, ... } })`.
  - الطلب الأول يحقق `count = 1` وينجح.
  - الطلب الثاني يجد `count = 0` فيرمي فوراً `BadRequestException` بالعربية: «عملية أخرى نُفِّذت للتو على هذا العنصر، حدّث الشاشة وأعد المحاولة»، وتُلغى معاملته بالكامل.

---

## 2. ثغرة الإغلاق/الأرشفة بالتزامن مع الإحالة (Close vs Refer Race)
- **الموقع:** `CorrespondencesService.close()` بالتزامن مع `ReferralsService.create()`.
- **سيناريو التسابق:**
  - المدير العام يضغط زر "إغلاق المراسلة" (`close`).
  - في نفس اللحظة، نائب المدير أو مدير قسم يُحيل المراسلة (`create`).
  - الإحالة قرأت المراسلة قبل اكتمال الإغلاق ووجدت حالتها صالحة للإحالة.
  - النتيجة دون قفل أو إصدار: تصبح المراسلة مغلقة ولكن توجد إحالة جديدة مفتوحة ومعلقة عليها!
- **الحل الجذري المطبق:**
  - كل من `close()` و `refer()` يشترط تطابق `version` ويزيده بمقدار 1 ذرّياً.
  - ينجح الطلب الأسبق، ويفشل المتأخر بنظافة دون إفساد بيانات النظام.

---

## 3. ثغرة اعتماد مسودة الرد بالتزامن مع التعديل (Approve vs Update Reply Race)
- **الموقع:** `RepliesApprovalService.approve()` بالتزامن مع `RepliesService.update()`.
- **سيناريو التسابق:**
  - الموظف يعدل نص المسودة ويحفظها.
  - في نفس اللحظة، يعتمد المدير المسودة القديمة قبل حفظ التعديل الجديد.
- **الحل الجذري المطبق:**
  - سجل الرد يحمل عمود `version Int @default(1)`.
  - الاعتماد يشترط `where: { id, version: reply.version, status: SUBMITTED }` ويزيد الـ `version`.
  - أي تعديل للمسودة يزيد الـ `version` فيحمي الاعتماد من اعتماد نسخة قديمة مبدلة.

---

## 4. ثغرة حساب مستلمي الإشعارات بالقراءات الحرة بعد المعاملة
- **الموقع:** حساب مستلمي الإشعار (مثل مديري الأقسام أو المعتمدين) خارج المعاملة بعد الالتزام.
- **الحل الجذري المطبق:**
  - استخدام نمط **صندوق الأحداث المعاملاتي (Transactional Outbox)**:
  - تُكتب حمولة الإشعار ومستلموها داخل نفس المعاملة المصرفية الذرية في جدول `EventOutbox`.
  - يضمن ذلك أن معطيات الإشعار متطابقة بنسبة 100% مع لحظة الالتزام، ولا تتأثر بأي تغيرات لاحقة.
